# Screen-to-screen 延迟测试方案

## 目标

在 Aura + MIA1321 单路 1280×1080、100 fps 采集已经稳定的基础上，测量从**被摄显示器实际发光**到 CachyOS 接收端显示器实际发光的延迟。该数值包含传感器曝光、VI/ISP、H.264 编码、以太网、H.264 解码和显示提交；它才是遥操作中应报告的 screen-to-screen 延迟。

发送端和接收端内部的时间戳仍然保留，但只用于定位瓶颈。两端并不共享时钟时，不能把它们相减并称为单向延迟。

## 结论：做一个原生的 `latency-stimulus`，不使用浏览器

新增一个只在 CachyOS 宿主机编译、运行的 C++20 程序 `latency-stimulus`。它与现有的 `host-viewer` 同属本机显示端，使用 SDL3 + Vulkan；不进入 Distrobox，也不依赖浏览器。

浏览器很适合临时观察画面，但其 JavaScript 定时器、渲染合成和浏览器自身的帧队列不能精确控制或记录。已有 viewer 已经使用 SDL3/Vulkan，测试图也应采用相同的原生显示栈，这样可以明确控制窗口模式、swapchain present mode 和待显示帧数量。

程序不需要额外的字体或图形库：数字使用内置七段码绘制，色块、二进制码和网格由 Vulkan 几何图元绘制。这样避免为测试图引入 SDL_ttf、浏览器或字体渲染的变量。

## 测试布置

推荐先用一台显示器完成闭环：

```text
CachyOS 显示器（同一面板）
┌──────────────────┬──────────────────┐
│ latency-stimulus │   host-viewer    │
│ 当前光学时间码    │ 摄像头返回的画面  │
└────────┬─────────┴─────────┬────────┘
         │ Aura 镜头只拍左半边 │
         └── Aura → 千兆以太网 → CachyOS

外部 240 fps 或更高帧率的手机/相机，同时拍摄显示器左右两半
```

Aura 镜头只取左侧测试图；`host-viewer` 在右侧显示它收到的画面。外部高速相机不参与传输，只记录同一时刻左边的当前时间码和右边图像内较旧的时间码。两码的差就是 optical screen-to-screen 延迟，因而不要求 Aura 与 PC 的系统时钟同步。

若单屏空间不足，可使用两块固定刷新率相同的显示器。高速相机必须同时看见两块屏幕，并让两个时间码处在大致相同的垂直位置，降低 LCD/OLED 自上而下扫描带来的偏差。

## 测试图内容

`latency-stimulus` 每次提交一帧测试图时采样 `CLOCK_MONOTONIC_RAW`，并绘制：

1. 中央的大号 `HH:MM:SS.mmm` 单调时间码，至少占图像高度的 25%，供人眼直接读数；
2. 同一个毫秒计数的 16 位 Gray-code 方格。它比十进制字体更容易在压缩画面、手机录像或逐帧脚本中可靠读出；
3. 单调递增的显示提交序号，以及每 100 帧翻转一次的黑白边框，便于识别卡帧和重复帧；
4. 四角定位标记、细网格和纯色区域，用于检查镜头对焦、曝光、裁剪、缩放和 H.264 宏块伪影。

时间码的值表示“该测试图被 CPU 提交给 Vulkan”的时刻，而不是假称为面板已经发光的时刻。真正测量时，在外部高速视频同一帧中读取左侧的当前码和右侧解码画面的旧码；同一面板、相同行附近的扫描误差会大部分抵消。

## 显示控制

首版应支持：

```text
latency-stimulus --width 960 --height 1080 --x 0 --y 0 --refresh-hz 120
host-viewer      --width 960 --height 1080 --x 960 --y 0 --borderless
```

窗口尺寸和位置只是示例，以实际面板分辨率为准。两程序需要支持无边框窗口、显式位置和固定大小；不要求测试图独占全屏。Vulkan swapchain 优先 `MAILBOX`，可用时只保留一个待显示画面；不能支持时记录回退到 FIFO。测试期间关闭 VRR、屏保、夜间色温、桌面动画和显示器的运动插帧，固定到已知的 120 Hz 或更高刷新率。

测试图按每次成功 present 更新，而非用 1 kHz 忙循环强制刷新。100 fps 的相机配合 120/144 Hz 面板可以观察到各阶段的帧量化；若面板只有 60 Hz，显示端本身会引入约 0～16.7 ms 的量化，不能据此判断 100 fps 管线的极限。

## 实施轮次

### 第 1 轮：可读的光学基准

- 新增 `src/latency-stimulus/`、CMake option `TELEOP_BUILD_LATENCY_STIMULUS` 和 `tools/build-host` 集成；
- 用 SDL3/Vulkan 绘制七段时间码、Gray code、帧号和定位图；
- 支持 `--window-x`、`--window-y`、`--width`、`--height`、`--borderless`、`--present-mode`；
- 在终端每秒报告渲染帧率、成功 present 数和所选 present mode；
- 增加 `tests/latency/README.md` 的运行、录像和人工读数步骤。

验收是：本机能稳定显示测试图，Aura 对左侧窗口采集的画面中能清楚读到所有数字和 Gray code；外部手机慢动作录像可同时读出左右码。

### 第 2 轮：完整 H.264 闭环

- 用现有 `aura-sender` 运行已验证的 100 fps VI → VENC 配置；
- `host-viewer` 采用 VAAPI → DRM PRIME → Vulkan 显示路径，窗口放在右侧；
- 保持 H.264 无 B 帧、低延迟 slice/wrap，接收端实行 newest-frame-wins；
- 每组参数至少录制 10 秒，逐帧取样，报告 P50、P95、P99、最小值和最大值。

先记录一组“整帧、保守队列”的稳定基线，再单独启用 wrap、slice、缩小缓存等改动。每次只改一个因素；遇到画面破损、帧号跳变或 IDR 恢复，结果单列为不合格，不以较低延迟掩盖。

### 第 3 轮：自动读码和分段归因

测试图稳定后，再写一个离线脚本读取手机慢动作录像中左右两组 Gray code，自动生成延迟直方图和百分位数。自动化不阻塞第 2 轮：首轮用人工逐帧读大号毫秒码即可。

同时输出以下软件侧数据，用于解释光学结果而非替代它：

| 区间 | 记录点 | 用途 |
|---|---|---|
| VI/编码 | VENC packet 获取时刻 | 定位采集到编码输出的代价 |
| 网络 | 首包、末包、重组完成时刻 | 定位传输与重组抖动 |
| 解码 | packet 提交和 frame 得到时刻 | 定位 VAAPI 解码代价 |
| 显示 | Vulkan 提交与 present 结果 | 定位软件展示队列 |
| 光学 | 左右时间码差 | 最终唯一的 screen-to-screen 结论 |

## 外部录像与判读规范

- 高速相机优先 240 fps（每帧约 4.17 ms）；120 fps 只能提供约 8.33 ms 的量化精度；
- 手动锁定高速相机的曝光、焦点和白平衡，避免自动曝光将屏幕闪烁误当作延迟变化；
- 让时间码位于两窗口相同高度，且避免拍到过大的倾斜角；
- 在录像的每一帧计算 `左侧当前毫秒码 - 右侧画面中的毫秒码`；Gray code 与十进制读数不一致时舍弃该样本；
- 丢帧或异常恢复应作为独立事件统计，不能混入稳态 P50/P95；
- 记录面板刷新率、相机采样率、Aura 采集帧率、分辨率、码率、GOP、wrap/slice 参数和 CPU/GPU governor。

首轮的报告应写成例如：`100 fps capture, 120 Hz panel, 240 fps reference camera: P50 31 ms, P95 39 ms, N=...`，并明确它是光学测量。不要把 host 日志中的 sender-to-decoder 微秒值混写为 screen-to-screen。

## 不纳入基准的路径

GStreamer、浏览器 WebRTC、桌面录屏和软件解码可作为功能诊断工具，但不进入首个低延迟基准。它们各自有时钟、合成或队列策略，会使结果难以归因。等原生 H.264/VAAPI/Vulkan 基线得到可靠数字后，才可把它们作为对照组运行同一张测试图。
