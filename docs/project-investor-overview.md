# 低延迟双目视觉遥操作

## 项目核心介绍与技术进展

**项目工作名：Luckfox Aura Teleop**

**版本：投资人交流稿 · 2026年10月15日**

> 为机械臂与机器人遥操作建立一条高帧率、低延迟、可持续优化的视觉回传链路。
> 当前实机演示的 screen-to-screen 延迟可稳定在 **25–35ms**；双路 **720p、约120fps**
> 的采集、硬件编码、网络回传与本机硬件解码已完成短测验证。

## 一、项目解决什么问题

机械臂遥操作需要操作者依据视频判断位置、接触和运动状态。视频反馈越滞后，
操作者越容易在动作已经发生变化后才看到结果，需要更多停顿、确认和修正。
对于近距离操作、快速移动和需要空间判断的任务，视觉链路的响应速度与连续性直接影响操作体验。

本项目聚焦于这条反馈链路：在设备端采集两路全局快门图像，完成硬件编码，
通过网络回传，在操作者计算机上硬件解码并显示。目标是在可部署的嵌入式平台上，
兼顾低延迟、高帧率、可接受画质和可控带宽，为后续机械臂双目遥操作提供视觉基础。

当前已形成可运行的软硬件原型，涵盖相机驱动、嵌入式系统、发送程序、传输协议、
接收显示程序和测量工具。项目现阶段验证的是**视觉回传能力**，尚不包含机械臂执行器、
控制指令和力反馈的完整闭环性能。

## 二、当前已验证的核心表现

| 指标 | 当前结果 | 验证说明 |
|---|---|---|
| Screen-to-screen视觉延迟 | **可稳定在25–35ms** | 项目团队在现有网线直连、144Hz显示器演示环境中的光学验证结果 |
| 视频输入 | **两路全局快门相机** | 两颗AR0234，分别采集、编码和传输 |
| 单路分辨率 | **1280×720** | 两路均为720p |
| 双路帧率 | **每路约119.95fps** | 实际帧周期约8.337ms，编码与主机收帧节奏相符 |
| 相机有效读出 | **约4.90ms** | 当前双路CIF观测均值约4.894 / 4.897ms |
| 编码及网络配置 | **H.264，30Mbps/路** | 双路视频目标码率合计60Mbps；实际码率随内容与帧型变化 |
| 接收端处理 | **全程硬件解码，GPU显示** | FFmpeg/VAAPI与Vulkan显示路径已接通 |
| 最新120fps时序验证 | **480帧全部硬解** | 单路、双路有界测试合计；未发现重组丢帧或新增内核/CSI错误 |

**数据口径。** Screen-to-screen是源屏幕内容变化经摄像头拍摄、编码、传输、解码后，
在接收屏幕显示的可见时间差，覆盖比单独编解码更完整的视觉链路。
25–35ms为团队现有实机演示的稳定观察区间，不代表长期运行的P99或全场景服务保证。
双路120fps的自动化短测与该光学观察为不同测试记录，不合并宣称为同一套完整统计。
两路目前独立运行，尚未将硬件同步曝光和立体标定列为已完成能力。

## 三、技术架构与选型

### 3.1 从相机到屏幕的完整路径

```text
设备端
两路AR0234全局快门相机
  → MIPI CSI-2 / CIF / ISP采集与图像处理
  → Rockchip硬件H.264编码
  → C++发送程序与UDP分包

网络
千兆以太网直连

操作者端
C++接收程序：收包、校验与两路图像重组
  → 每路独立FFmpeg / VAAPI硬件解码
  → DMA-BUF图像共享
  → Vulkan / libplacebo渲染、SDL3窗口
  → 144Hz显示器
```

### 3.2 为什么采用这套技术组合

| 层次 | 当前选择 | 选择理由 |
|---|---|---|
| 边缘平台 | Luckfox Aura / Rockchip RV1126B | 利用现有ISP与专用视频编码硬件，在嵌入式设备上完成采集和压缩 |
| 图像传感器 | AR0234全局快门 | 减少逐行曝光带来的运动形变，适合关注运动状态的遥操作场景 |
| 相机接口 | 四通道MIPI CSI-2 | 已实测缩短有效图像读出时间，为高帧率双路输入提供基础 |
| 系统 | Linux 6.1 PREEMPT + Buildroot | 可以控制驱动、设备树、系统服务与部署内容，支持针对性调优 |
| 编码 | Rockchip RK MPI / MPP，H.264硬件编码 | 复用专用硬件，保持接收端兼容性；当前采用无B帧低延迟路径 |
| 网络 | 自定义轻量UDP视频协议 | 控制分包、完整帧边界与接收队列，避免在应用中引入额外帧等待 |
| 核心应用 | C++原生sender / viewer | 便于精确控制线程、缓冲区、设备接口与每个阶段的测量 |
| 解码及显示 | FFmpeg、VAAPI、Vulkan、libplacebo、SDL3 | 将硬件解码与GPU显示衔接，并保留对显示节奏和队列的控制 |

当前优先使用有线直连建立可重复的性能基线。未来无线回传会复用参数化的应用架构，
根据实测吞吐、抖动和丢包情况选择码率与编码策略；无线性能尚未作为当前成果对外承诺。

### 3.3 从USB摄像头组合到MIPI一体化边缘视觉

项目的优化从硬件和系统架构选择就已经开始。相机通过MIPI直接进入RV1126B的采集与ISP路径，
再送入专用编码硬件，能够在同一设备上管理曝光、读出、图像处理与编码，
减少对独立USB相机内部固件、缓存和输出格式的依赖。
与“USB相机输出压缩图像→主机解码→为网络回传再次编码”的组合相比，
本项目采用RAW输入、ISP处理后直接硬编，避免该类组合中的中间解码与重编码。
若USB相机本身输出原始图像或可直接转发的适用码流，则不一定存在上述重复步骤。

| 市场上可见的方案 | 已有能力与适用性 | 本项目的差异化方向 |
|---|---|---|
| 消费级USB网络摄像头，例如Logitech C920e | 官方规格支持720p/1080p、30fps，便于视频会议接入 | 当前双路720p约120fps，每路图像更新频率约为该例的4倍；同时控制底层采集与回传 |
| 工业USB 3.0相机，例如Basler acA2040-90uc | 已提供全局快门，适合工业采集；USB也可承载高性能视觉 | 我们交付的是从相机、ISP、硬编到网络和显示的整条遥操视觉链路，而非仅相机接口 |
| 通用相机、编码盒与播放软件组合 | 可以快速组合出功能，但总延迟取决于每个设备和软件的缓存策略 | 在同一工程体系内控制帧边界、队列、码率和显示，已取得25–35ms级实机演示结果 |

C920e规格见[Logitech官方资料](https://secure.logitech.com/content/dam/logitech/en/video-collaboration/pdf/c920e%20datasheet.pdf)，
工业USB全局快门例见[Basler官方资料](https://docs.baslerweb.com/aca2040-90uc)。
上述比较是产品定位与公开规格比较，尚未对这些商品做同条件端到端延迟测试。
MIPI的核心优势在于本项目的直接集成与可调优程度；接口名称本身不保证快于所有USB方案。

### 3.4 RV1126B的ISP与MPP平台为什么重要

RV1126B集成ISP、视频处理和H.264/H.265专用编解码模块，
为设备侧完成成像处理和压缩提供硬件基础。
[Rockchip官方平台说明](https://www.rock-chips.com/?id=533)

**ISP负责把传感器输出转为下游可用图像。** 本项目将MIPI采集、ISP和视频编码串联，
由硬件处理链路输出编码所需的图像格式，减少CPU承担整幅原始图像处理和搬运的需求。
ISP还为未来画质调校保留空间；当前并未把完整自动曝光、自动白平衡或AI降噪调优列为已完成成果。

**MPP/RK MPI负责调用专用编码硬件。** 双路720p、名义120fps的RAW10有效像素数据量约为
2.21Gbit/s，尚未计接口开销；当前通过硬件H.264压缩为目标合计60Mbit/s的视频流，
才便于经千兆链路回传，并为未来无线适配留出路径。两者是输入与输出的数据量对照，
不表示无损压缩率。曝光、ISP、硬编和网络可以在边缘设备上分工完成，
当前发送链路不依赖一台额外的桌面GPU计算机。

这一选择的价值在于系统集成：专用硬件承担持续像素处理，CPU管理协议、线程与设备控制，
接收端GPU负责硬解与显示。功耗、BOM成本和相对竞品成本仍需独立测算，本文不作未经验证的百分比承诺。

## 四、性能优化已经取得什么成果

硬件选型、全局快门、MIPI直连ISP和专用硬编构成第一层优化；下面是其上已经完成的
驱动、协议、线程和内存路径优化。全局快门减少逐行曝光的运动形变，但运动模糊仍受曝光时长影响。

### 4.1 消除软件中隐藏的“多等一帧”

早期链路中，发送端需要等待下一帧来确认当前帧结束，接收端解析器也存在类似的帧边界等待。
这些等待并非相机或编码器本身的必要开销，却会直接增加图像年龄。

目前已改为编码器返回完整视频帧后立即发送，接收端收齐完整帧后立即提交硬解。
在原约99fps配置的A/B中：

| 阶段 | 优化前均值 | 优化后均值 |
|---|---:|---:|
| sender最后编码包就绪→准备发送，两路 | 约7.86 / 7.88ms | 约0.11 / 0.13ms |
| host完整帧就绪→提交解码，两路 | 约9.99 / 10.03ms | 约0.002 / 0.003ms |

两项软件阶段等待合计减少约**17.7ms**。这是同阶段软件计时的对照结果，
不等同于独立测得的screen-to-screen减少17.7ms，也不与下面的优化数值直接累加。

### 4.2 从传感器读出入手，把约9.79ms压到约4.90ms

项目已完成AR0234驱动与板端适配，并将两路相机由原两通道模式迁移到已验证的四通道快速读出模式。
在保持约99fps帧率、固定物理曝光进行对照时，CIF有效读出均值由约**9.79ms降到4.88–4.89ms**，
减少约**4.90ms，接近减半**。

随后进一步缩短帧间空白，将帧周期从约**10.078ms降到8.337ms**，
双路实际帧率提升至约**119.95fps**。当前曝光约5ms，并通过手动增益维持可用亮度。
帧率提升与读出加速分别验证，避免仅调整编码器的声明帧率却没有真正提高相机输出。

全局快门仍需要逐步传出图像数据；曝光、读出和下游处理存在流水关系，
因此本项目分别测量这些阶段，不把“曝光完成”视为“整幅图像已可显示”。

### 4.3 收包、解码、显示解耦，避免慢显示拖住整条链路

接收端采用独立收包线程、每路独立解码线程和显示主线程。
显示端使用每路最新已解码帧，避免因一次较慢的GPU或窗口调用让两路网络接收一起积压。

同时，压缩视频队列有明确容量和观测指标，不通过随意丢弃H.264参考帧来制造低延迟。
最新双路120fps短测中，每路待解码队列峰值均为**1帧**，队列等待均值约**9 / 13微秒**，
未见持续积压或溢出。

### 4.4 非阻塞批量收包，降低CPU开销

接收端使用非阻塞批量收包：一次处理当前已经到达的多个UDP报文，
不等待凑满批量，也不为合并报文额外增加定时等待。

在原约99fps双路对照测试中，选用批量上限16后，接收系统调用次数约减少**57%**，
每报文CPU成本约下降**24%**，对应测试中的接收尾部指标未明显恶化。
这项收益主要体现为CPU效率与调度余量，不能解释为端到端延迟下降24%。

### 4.5 打通关键图像共享路径

设备端通过DMA-BUF与系统绑定接口连接采集、ISP和编码资源，避免应用先取出整幅原始图像再复制给编码器。
接收端将VAAPI硬解图像经DMA-BUF共享给Vulkan，避免应用层像素下载到CPU后再次上传GPU。

这降低了大幅图像搬运的需求。压缩码流仍需网络传输与重组，硬件间也仍需正确同步，
因此项目将其表述为**关键图像路径共享**，而不宣称所有环节都不存在拷贝或等待。

### 4.6 从通用SDK走向可控的专用系统

项目以Buildroot管理设备端系统，以摄像头驱动与设备树补丁固化两路接入和传感器时序，
将通用开发板配置逐步收敛为遥操视觉工作负载。当前内核启用PREEMPT可抢占配置和1000Hz时钟，
为响应性调优提供基础；1000Hz不是“整条链路只需1ms”的含义。

同时已对内核功能裁剪、调度亲和性、实时优先级和电源偏好开展单变量A/B，
将镜像体积、资源占用与延迟分别记录。该过程形成的能力是可以定位瓶颈、验证改动并回退，
后续可根据部署需要继续精简系统，而不是要求操作者计算机承担设备侧所有处理。

## 五、延迟链路已经测到了哪里

除整体光学观察，项目还建立了分阶段的测量方法，以区分真正的处理时间、等待时间与异步API返回时间。

| 测量对象 | 已验证结果 | 测量条件与含义 |
|---|---:|---|
| 整体screen-to-screen | **稳定25–35ms** | 当前有线直连、144Hz实机演示；团队光学观察 |
| 当前曝光 | **4.998ms** | 735行 × 6.8µs/行；是积分时长，不是整链路延迟 |
| 当前双路CIF有效读出 | **约4.90ms** | 120fps配置的接收侧帧开始→帧结束观测 |
| 当前双路帧周期 | **约8.337ms** | 是相邻帧间隔，不是单帧在系统内的停留时间 |
| 硬件H.264编码工作时间 | **均值约2.51ms** | 此前约99fps配置，读取编码器实际硬件周期计数 |
| 双路H.264解码完成时间 | **均值约1.83ms** | 此前真实码流双路回放，提交完整帧至VAAPI surface实际完成 |
| 当前host待解码队列等待 | **均值约0.009 / 0.013ms** | 两路120fps短测，完整帧就绪后等待解码线程 |

这些数据来自不同测量边界，部分采用不同配置与回放条件，**不能逐项相加构造25–35ms的“精确拆账”**。
例如帧周期不是每帧必须额外等待的时间，GPU返回帧对象也不代表图像已经完成解码或屏幕已经发光。
跨设备的单向网络延迟尚未用同步时钟单独验证。

144Hz屏幕每次刷新约6.94ms，显示时机、屏幕扫描、相机采样相位和曝光都会影响最终可见时间差。
因此，后续优化同时关注阶段完成时间与最终光学结果，避免仅让某个软件统计数字变小。

## 六、可交付的工程基础

项目已将原型整理为可继续迭代的工作区：

- **应用源码与可复现补丁。** sender、viewer、驱动和设备树修改、系统配置、构建脚本与测试摘要统一管理；
  锁定厂商SDK的63个子仓库版本，并支持补丁检查与隔离重放。
- **分离的构建环境。** 设备端使用Ubuntu 22.04容器交叉编译；接收端在原生Linux环境构建，
  降低宿主GPU和显示库不匹配的问题。
- **双路资源管理与故障验证。** 两路共用单进程媒体系统会话，使用独立通道；
  已修复发现的中断共享锁问题，并开展初始化失败、信号退出、重复启动与资源回收的有界回归。
- **测量与回退能力。** 保存配置、二进制指纹、镜像清单和A/B结果，使用独立USB日志协助诊断；
  参数改动可以复测和回退，而不是依赖一块开发板上的临时手工状态。

内核裁剪、电源策略和调度也已进行独立对照。裁剪候选曾使启动镜像缩小约0.91MiB，
但尚未证明稳定的整体延迟收益；当前快速读出配置并未默认叠加该裁剪候选。
对于没有一致收益的性能开关，项目保留实验入口，不增加默认复杂度。

现阶段已具备实机演示和短时回归能力。长时间运行、不同环境温度、无线网络扰动与现场可靠性
仍是后续验证重点，不将短测通过等同于完成产品级可靠性认证。

## 七、下一阶段：有约束地以带宽换延迟

下一轮从现有H.264链路继续挖掘性能，优先复用当前硬件，保持配置可切换：

| 方向 | 下一步工作 | 评估标准 |
|---|---|---|
| 减少编码计算与率控等待 | 对照GOP=1、固定QP、禁止重编码；再测熵编码、变换与去块滤波 | 实际硬件周期、GPU完成时间、画质及码率 |
| 接收端KMS直接显示 | 研究绕过桌面合成器的DRM/KMS专用显示后端 | 解码完成→实际翻页/扫描的时间，及尾部等待 |
| 让编码与传输重叠 | 验证可靠的slice末片标记，再研究渐进发送 | 不重新引入帧边界等待，画面与丢包处理正确 |
| 控制带宽成本 | 先测30→40→60Mbps/路，选择有效的最低档位 | 兼顾平均码率、I帧突发、排队与延迟收益 |
| 面向无线回传 | 实测板载无线链路的吞吐、抖动、重传与恢复 | 为有线与无线建立不同参数配置 |
| 面向更完整的双目遥操 | 推进标定、同步策略、双目显示与机械臂系统集成 | 图像时间一致性、操作体验和任务表现 |
| 产品化验证 | 长时间运行、热稳定性、异常恢复和部署维护 | 可重复运行与现场可维护性 |

PyroWave等方案提供了“用更多带宽换更少编解码计算”的参考方向。
当前平台先研究可由现有硬件完成的全I帧、固定QP与slice流水；
PyroWave本身及约0.2ms级编解码尚未在本项目平台实现，不列为现有性能。
未来若更换具备合适可编程GPU与高速网络的平台，可继续沿用现有测量体系评估新编码方案。

### 7.1 KMS直出：减少桌面显示路径中的可变等待

计划在现有桌面窗口后端之外，增加面向专用遥操终端的DRM/KMS后端。
优先检查能否将已解码DMA-BUF直接交给显示plane；若双路布局、旋转、缩放或格式不被plane支持，
则先用GPU合成到可扫描输出缓冲，再由KMS提交。两条路线都需要正确的硬件完成同步，
不能通过省略fence让显示读取尚未完成的图像。

KMS有机会减少桌面合成器排队和额外合成步骤，但不会消除显示刷新与面板响应。
144Hz每周期仍约6.94ms；扫描到目标像素的位置也影响可见时刻。
将先只读检查显示硬件能力，再在专用会话或可用显示租赁机制下做对照，保留桌面viewer。
实现依据为[Linux DRM/KMS接口与同步文档](https://docs.kernel.org/gpu/drm-kms.html)。

本项目把KMS收益先视为**待争取减少约0–一个刷新周期的排队**，而非已证实固定节省6.94ms。
如果当前桌面已经走较好的直接扫描路径，实际收益可能接近零；更确定的价值是提高专用终端的
显示路径可控性，并通过翻页事件与光学测试定位尾部等待。

### 7.2 优化后的阶段预算

下表是研发目标与算术预算，**不是新增测试结果，也不是各阶段P99保证**。
假设保留双路720p约120fps、当前约5ms曝光、千兆直连、144Hz屏幕，
并接受适量增加码率。编码与解码的现有参考仍来自此前约99fps测试，下一轮先重建120fps基线。

| 环节 | 当前依据 | 优化后规划值或保持值 |
|---|---|---|
| 曝光 | 当前4.998ms | 保持约5ms；照明充足时另试1–3ms，不以画面过暗换数字 |
| 有效图像读出 | 当前约4.90ms | 保持约4.90ms；进一步降低需改变传感器时序或有效成像区域 |
| CIF/ISP输出至编码开始的额外等待 | 尚未完成可靠逐帧关联 | 预算0.3–1.5ms，需插桩核实；若存在整帧等待，应重新评估 |
| 硬件编码工作时间 | 历史均值约2.51ms | 目标约1.5–2.2ms，依靠参数A/B确认，硬件下限可能限制收益 |
| 有线发送、传输与接收重组 | 尚无同步跨机单向实测 | 正常负载预算约0.3–1.2ms；核对双路突发及排队 |
| 主机待解码队列 | 当前均值约0.009 / 0.013ms | 维持均值低于0.1ms，避免持续积压 |
| 完整帧提交至GPU解码完成 | 历史双路均值约1.83ms | 目标约1.0–1.6ms，需要实际surface完成测试 |
| KMS导入/必要合成/提交的额外处理 | 尚未实现KMS后端 | 预算约0.2–1.0ms，不含等待刷新和屏幕扫描 |
| 等待144Hz显示时机 | 一个周期约6.94ms | 理想无额外排队时约0–6.94ms，随机相位均值约3.47ms |
| 屏幕扫描到目标像素 | 尚未实测扫描方向与时间 | 预算约0–6.94ms，与目标位置和屏幕物理扫描方向有关 |
| 面板像素响应 | 未独立测量 | 暂留约1–4ms工程余量，最终由所用面板实测决定 |

表中曝光、读出与处理可能存在流水重叠，采样相位也随测量口径变化；
不能把每项最小值相加当作可实现的极限，也不能将刷新等待的最大值当作每帧固定开销。
120fps采集还存在最多约一个帧周期的采样相位差，该时间不等同于处理时间，
尚未纳入同一帧的完整时间戳关联。对未知环节给出的预算用于指导测量，不能替代测量。

在这些假设下，近期把有线screen-to-screen从当前稳定**25–35ms**进一步推进到
**约20–30ms**，作为待验证的阶段目标较为合适；不是将各项独立节省简单相减所得的承诺。
若照明允许缩短曝光、KMS确实减少额外排队，并进一步匹配采样与显示节奏，
可探索**15–25ms**区间，但应列为挑战目标，不列为当前或近期必达指标。
若硬件编码参数或KMS没有带来预期收益，保留现有配置，不为达标牺牲画质与正确性。

### 7.3 无线图传：建立独立的带宽、延迟与恢复配置

第一步复用板载无线芯片，验证驱动、工作模式和可用吞吐；随后在明确距离、视距、
频段及干扰条件下测双路回传。优先采用单跳专用链路，避免未经测量就叠加多跳转发。
无线配置与有线分开，码率根据实际应用吞吐和突发余量确定，不照搬链路标称速率。

先以**10–20Mbps/路**作为待验证的起始码率范围，再按画质和链路余量调整。
GOP1和FIXQP可能产生较大流量突发，不直接作为无线默认；需要对照有界码率、
IDR请求与丢包后恢复策略。对无法完整恢复的参考帧应明确处理，避免长时间花屏或积压旧图像。
FEC、重传和帧丢弃策略分别测量，按时效性决定是否值得恢复，避免无限等待过时画面。

在短距、低干扰、专用单跳的假设下，先为无线单向传输、重组与必要恢复留出
**约2–8ms的研发预算**；该值尚未在板载芯片验证，不是通用Wi-Fi延迟指标。
相比有线预算，预计会多占用约数毫秒，并可能有更长尾部。
可先以**约25–40ms screen-to-screen**作为受控无线演示的规划目标，
待有线优化与无线短测都完成后再收敛；不同地点、干扰和距离下不保证此范围。
受干扰或需要多次重传时可能明显超出，届时优先降低码率或帧率并报告尾部数据，
而不是扩大缓冲区维持“看起来流畅但已经过时”的画面。

## 八、阶段价值与落地路径

项目当前的阶段价值，是在真实嵌入式硬件上验证了一条**25–35ms级视觉反馈**的可运行路径，
并把传感器、驱动、媒体硬件、网络和显示端连接成可测量、可复现的系统。
优化成果不仅来自更换算力平台，也来自识别并消除不必要的等待、缩短相机读出、控制队列和打通硬件共享。

近期适合围绕固定工位、可走网线的机械臂遥操作开展联合演示与任务验证；
随后依据实际任务对双目同步、画质和可用性的要求，推进系统集成与无线版本。
潜在交付形态包括视觉回传模块、接收显示软件，以及面向具体机器人平台的适配和调优服务。
这些属于后续产品化路径，本文不将其表述为已签约客户、收入或已验证商业规模。

下一阶段资源重点应投入可重复的任务演示、长时间可靠性验证和编解码优化，
把现有技术原型推进到可供合作方集成评估的视觉子系统。
