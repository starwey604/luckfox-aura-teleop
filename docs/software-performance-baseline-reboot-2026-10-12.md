# 旧内核重启后：实机分段耗时与温度核对

本轮补齐了两个单路和一次冷启动双路的短测试，使用旧内核和上一轮的计时版程序。
同时再次复现失联；当前证据优先指向启停/初始化相关问题，**没有证据确认 CPU 过热保护导致失联**。
按用户要求，后续只做短测，不再自动进行长测。

## 1. 实验条件与工具

内核仍为 `6.1.141 #12 SMP PREEMPT`，未改 SDK、镜像、频率、IRQ、NIC 或缓冲上限。
旧 `/userdata/teleop-sender` 保留；另部署 `/userdata/teleop-sender-metrics`，hash 与上一轮交叉构建一致。
viewer 在 CachyOS 原生运行，`--headless`、默认 VAAPI，`TELEOP_METRICS=1`。
两路都是 1280×720、目标 100 fps、30 Mbit/s、GOP 15、slice 120、wrap=0，固定曝光/增益同前。

新增 `tools/test-aura-software-baseline`：

- 在开始 sender 前确认 viewer 进程存在、UDP 端口已绑定，不靠人工切换两个终端的时间差。
- 拒绝已有摄像头程序和被占用的端口，不停止用户其他程序。
- 在本机保存板端 before/after 快照、约 1 Hz 的 CPU/线程/温度/UDP 采样、sender/viewer 输出与 `result.json`。
- 双路提前创建报告目录并 `sync`，同时镜像日志到本机；避免锁死后文件目录尚未提交而丢失。
- 有远端 timeout 和本机超时；不自动重启或烧写。超时不能解除一个已经卡死的内核。
- 默认 **120 帧/路**，超过 300 帧默认拒绝；启动温度 **≥50°C 默认拒绝**。
  50°C 是本项目无风扇短测的保守门槛，不是芯片硬件热保护阈值。
  `--allow-long` 只留给用户后续安排散热并明确进行长测时手动使用，本轮之后不自动使用。

所有 raw logs 位于 `logs/latency/B0-reboot-20261012/`，继续 ignore。

## 2. 实机短测结果

| 测试 | 返回/解码 | 重组错误 | 最后采到的最高温度 | 结束后 SSH |
|---|---|---|---:|---|
| camera0 单路 300 帧 | 300/300，全部硬解 | 0 | 44.80°C | 正常 |
| camera1 单路 300 帧 | 300/300，全部硬解 | 0 | 45.64°C | 正常 |
| 同一次开机中，单路测试后启动双路 300/路 | 未完成 | 无可用最终统计 | 45.84°C | 失联 |
| 再次重启后的首次双路 300/路 | 共 600 AU，两路各 300/300，全部硬解 | 0 | 48.78°C | 正常 |
| 随后第二次启动双路，目标 6000/路 | 初始化/出流后失联，未完成 | 无可用最终统计 | 49.54°C | 失联 |

通过的双路短测：16973 datagrams、20034511 bytes，malformed/duplicate/dropped 均为 0。
CPU `/proc/stat` 采样以四核合计为 100%，包含采样本身、启动和收尾：单路平均约 3.5%，
成功双路短测平均约 7.8%，最高采样约 15.6%。sender 单进程最大 RSS 约 7.6 MiB。
失联前的记录仍显示大量 CPU 空闲，未看到简单的 CPU 满载或内存耗尽证据。
这些短样本不构成长时间稳定性证明，也不证明热故障绝不存在。

## 3. 双路短测的软件阶段

下表全部来自**真实板端与直连网线**，不再是 localhost 回放。
每阶段独立计时，P50/P95/P99 是直方图上界，不能直接把各阶段百分位相加称为完整链路延迟。

| 阶段 | camera0 P50/P95/P99 ms | camera1 P50/P95/P99 ms |
|---|---|---|
| 编码 AU 相邻输出间隔 | 10.0925 / 10.3547 / 10.4250 | 10.0925 / 10.2236 / 10.3547 |
| 首 pack 到最后 pack | 2.1955 / 2.2610 / 2.3265 | 2.2282 / 2.2610 / 2.2938 |
| 最后 pack 等下一 PTS 确认边界 | 7.9299 / 8.1920 / 8.3886 | 7.9299 / 8.1265 / 8.2575 |
| 首 pack 到开始发送完整 AU | 10.0925 / 10.3547 / 10.4291 | 10.0925 / 10.2236 / 10.3547 |
| packetize/sendmmsg 排队调用 | 0.3482 / 0.6308 / 0.7045 | 0.3277 / 0.5980 / 0.6308 |
| 主机首数据报到 AU 重组完成 | 0.2785 / 0.5734 / 0.6390 | 0.2703 / 0.5489 / 0.5816 |
| 主机 parser 等待 | 10.0925 / 10.4858 / 10.7479 | 10.0925 / 10.4858 / 10.6168 |
| 解码 packet 提交到 VAAPI frame 返回 | 0.0809 / 0.1823 / 0.2621 | 0.0881 / 0.1905 / 0.2703 |
| 主机完整 AU 到 frame 返回 | 10.2236 / 10.6168 / 10.8790 | 10.2236 / 10.6168 / 10.7479 |

输出间隔均值约 10.076/10.077 ms，即约 99.24/99.23 fps；与原始采集一致。
每路只有 300 个 AU 样本，P99 的统计信心仍有限。
VAAPI frame 返回未等待 GPU 完成 fence，不能把这个 API 耗时称为硬件完整解码时间。
UDP 排队与重组间隔也不是跨机单向网络延迟；没有用未同步的板端/主机时钟相减。

**不能漏报尾帧异常：** camera0 的 `parser_wait` 最大 1152.82 ms，
`au_ready_to_frame` 最大 1152.89 ms、平均 14.009 ms。
camera0 的有限帧发送先结束，但它的最后一个 AU 要等 viewer 收完 camera1 后统一 flush；
这约 1.15 秒的尾帧等待与错开的启动/结束时刻吻合。
它不是持续 99 fps 段的常见延迟，却是现有停流行为的真实缺点；没有默默删掉该样本。
完整 AU 网络入口去掉 parser lookahead 既可能省下一帧稳态等待，也可能改善这种停流尾帧等待，后续单独验证。

## 4. 温度是否造成失联

用户提醒无风扇可能过热后，立即对正在运行的冷启动长测发送 SIGINT 停止。
当时 SSH 正常、`cpu-thermal` 为 **55.18°C**；读取到唯一 thermal trip：

```text
trip_point_0_type = critical
trip_point_0_temp = 115000  # 115°C
```

不是把 CPUFreq governor 是否存在当作温度证据；这里使用实际 sysfs 读数和阈值。
先前失联前的采样峰值分别为 45.84°C、49.54°C；没有取得失联瞬间的全部数据，
但这些读数不符合“已接近 115°C 临界热保护”的特征。
目前判断是：**证据不支持 CPU 达到临界温度并触发保护；不能因此完全排除其他部位的局部热问题或温度参与的不稳定。**
CPU 传感器只测一个热区；加散热后同条件短测对照，才能进一步区分这些因素。

冷启动直接长测在用户要求停止前已经编码 camera0=5796、camera1=5682 帧，
持续出流约 58/57 秒，板端响应始终正常；这是**主动停止**，不是第三次卡死。
runner 的 success=false/退出130 表示没有完成原定 6000/路的计数目标，不能误写成运行崩溃。
sender 已输出其完整局部阶段直方图；该版 viewer 被 runner 终止时不输出部分统计，
因此没有完整的长测主机解码计数，不能宣称 12000 AU 全部通过。
结束后未留下 sender/capture 进程，温度随后降至约 47.47°C。

长测 sender 样本显示：首 pack 到发送的 P50 仍约 10.09 ms，
下一 PTS 等待 P50 约 7.93～8.00 ms，UDP 排队 P50 约 0.33～0.34 ms。
没有为了得出低数字偷偷降低分辨率、帧率或码率。

## 5. 下一步与短测使用方式

当前最有用的优化线索仍是两个显式等待：板端 AU 完整性确认，以及主机 parser lookahead。
内核裁剪先保留原计划，但必须把可复现的初始化/资源回收问题与性能调优分开。
冷启动首次双路通过、后续重新启动失败的模式已出现两次；
它支持优先排查 SDK/驱动重复初始化及共享资源生命周期，**还不是确定的根因**。
下一轮诊断可在单次 SYS 初始化中管理双摄，以排除两个独立进程反复 init/exit 的影响，
也需复核停止顺序和残留 driver/session；本轮没有盲目改这些逻辑。

短测示例（先确认 SSH、已部署计时版、已冷却，输出目录必须是新的）：

```sh
./tools/test-aura-software-baseline --camera 0 \
  --output logs/latency/B0-short-camera0

./tools/test-aura-software-baseline --camera dual \
  --output logs/latency/B0-short-dual
```

有 SSH key 时直接使用；需密码时由用户在环境提供 `SSHPASS`，脚本用 `sshpass -e`，不把密码写入源码/报告。
两路共用的 5000 端口会先检查，不需要另外手动启动 viewer。
短测策略和温度门槛不解决内核锁死；出现失联就停止后续 camera 测试、保留本机日志，由用户手动恢复。

本轮验证包括：实机两个单路及冷启动双路短测；camera0/1 正确 stream ID、VAAPI 计数和零错误检查；
长帧数默认拒绝测试；故意设置 1°C 门槛的**只读**拒绝测试，确认没有启动 sender；
native 与 Distrobox Python 语法检查。日志、镜像和生成物继续排除 Git。
