# AR0234：720 行输出预算能否低于 9.8ms

后续已完成四通道实机短测，见[实现与A/B结果](ar0234-fastreadout-ab-2026-10-15.md)。
以下保留开始时的只读探索。

2026-10-15。结论：**有希望，优先验证四通道、90MHz 读出；当前两通道、45MHz、
720 行模式没有已确认的简单控件可以继续压缩这一预算。** 本轮核对 SDK 源码、
商家 INI、已有接线记录及公开驱动，没有访问或调整实机，也没有编译新镜像。

## 当前 9.8ms 的含义

商家 `[720P 99.2fps]` 与 SDK `ar0234-decxin-3478v1.h` 一致：
`0x300C=612`、`0x300A=736`、RAW10、两通道、450MHz link frequency。
驱动报告的 HTS=2448、pixel_rate=180MHz 是四像素时序换算；
不能把 180MHz 与传感器内部 45MHz 混用。

```text
行时间             = 612 / 45MHz = 13.6µs
720 个行时间       = 9.792ms
帧周期             = (736+5) × 13.6µs = 10.0776ms
帧率               ≈ 99.22998fps
当前 blanking 预算  = 21 × 13.6µs = 0.2856ms
```

9.792ms 是按模式时序得到的有效行输出预算，不是独立测到的“曝光结束到编码器”
固定延迟。精确 frame-valid/CSI SOF→EOF 还受首末行空白、包开销和内部时序影响。
曝光、读出和下游处理可能重叠；不能把曝光时间、9.792ms、整帧间隔再全部相加。

## 为什么直接减 blanking、改曝光或降 RAW 位深不够

- 当前 HBLANK=1168 来自 `612×4−1280`，是驱动的等效像素单位，且为只读。
  它不表示可随意删除 1168 个像素的空闲时间。公开的 Linux 驱动 RFC 把
  `LINE_LENGTH_PCK_MIN` 明确设为 612，与当前值一致，暂不将更小行长作为正常工作模式。
  [作者提交的 RFC](https://www.spinics.net/lists/devicetree/msg901623.html)。
- VBLANK 已在当前驱动允许的最小值 21，包含参考模型中的五行开销。
  即使假设删除全部这段预算，也只有 0.2856ms，而且不会缩短 720 个有效行时间。
- 曝光控件改变积分行数，不改变行时间；sender 的 `--fps` 也不会自动提升 sensor 读出 clock。
- 公开参考驱动在两通道 RAW8/360MHz link 下仍采用 45MHz 读出，因此不能将
  RAW10→RAW8 当成读出时间自动减少 20%。改链路速率也需要配套 PLL、模拟与接收端配置。
  [参考驱动源码](https://github.com/Kurokesu/ar0234-rpi-driver/blob/main/ar0234.c)。

两通道 900Mbit/s/lane 的纯像素载荷下界是 `1280×720×10 / 1.8G = 5.12ms`，
未计 CSI 开销。它说明线上并非一直填满有效像素，但**不能证明** sensor 能把行时间
任意缩短到这个下界：内部读出、FIFO 和模拟时序另有限制。目前没有验证过的
DECXIN 两通道高速表支持这种改法。

## 首选：四通道与 90MHz 读出

当前 SDK 的通用参考分支已有 lane 数与读出时钟的对应关系：两通道 45MHz、
四通道 90MHz；RAW10 每 lane 仍为 900Mbit/s。公开 Kurokesu 驱动也列出四通道
720p 约 198.49fps 的模式，支持这一方向，但不是 DECXIN 模组在 Aura 上的验证结果。
[模式列表](https://github.com/Kurokesu/ar0234-rpi-driver/blob/main/README.md)。

| 保持 1280×720、行长 612 | 当前两通道 | 四通道候选 |
|---|---:|---:|
| 内部读出时钟 | 45MHz | 90MHz |
| 行时间 | 13.6µs | 6.8µs |
| 720 行预算 | 9.792ms | 4.896ms |
| 同为 741 总行时的帧周期 | 10.0776ms | 5.0388ms |
| 对应最大帧率估算 | 99.23fps | 198.46fps |

表内四通道值是使用当前商家行长/帧长模型推算，公开驱动的细小数值差异不代表
我们已经获得相同实测帧率。目标是将这一段预算减少约 **4.9ms**，端到端收益要另测。

硬件有依据：已有接线核对中，Aura H3/CSI0、H4/CSI1 与模组均引出了 D0–D3；
SDK 的板级说明将 `csi2_dphy0` 和 `csi2_dphy3` 分别对应独立 CSI0/CSI1 四通道接收。
当前双路使用的就是这两组，而不是同一组四通道拆分出的两个双通道端口。
见 [接线核对](ar0234-wiring-confirmation.md) 及 SDK
`arch/arm64/boot/dts/rockchip/rv1126b-luckfox-aura-cam-csi1.dtsi`。
这支持双路各四通道的实验条件；D2/D3 的实际连通与高速质量尚未实测。

实现不能只改 DTS 的 `data-lanes`：

1. 保留现有 DECXIN 两通道基线，新增独立可选择的四通道实验配置。
2. 审核商家完整初始化序列、两通道专用 sequencer 设置、`0x30BA` 的时钟/增益组合、
   `0x31AE`、PLL 与 MIPI timing；不能直接用通用参考初始化覆盖商家镜头/模拟校正。
   当前 DECXIN 配置明确拒绝四通道；必须连同控件时序和接收 endpoint 一起调整。
3. 同步更新真实 pixel_rate、曝光换算、帧间隔与 VBLANK 范围。仅改报告的 pixel_rate
   或解除四通道检查，不会让硬件变快。

**优先保持约 99.23fps 做公平对照，而不是直接让双路都翻倍到约 198fps。**
若 90MHz 模式工作正常，可按同一模型将总行数设为 1482：帧长寄存器 1477、
VBLANK=762，帧周期仍为 10.0776ms，有效输出预算仍为 4.896ms。
这是一组待验证的时序设计，不是现在可以直接执行的寄存器命令。
平均帧数保持不变，瞬时 sensor/ISP 数据率仍会上升，需检查双路共享 ISP 的调度与吞吐。
更长 blanking 也会改变曝光/读出相位，必须确认图像年龄，不能仅看 EOF 更早便宣称省了 4.9ms。

曝光按物理时间保持相同：行时间减半后，原来的 74/147/221 行应对应
148/294/442 行，分别保持约 1.0064/1.9992/3.0056ms；不要沿用原行数再比较亮度和延迟。

## 备选与下游重叠

| 方案 | 有效行预算估算 | 代价 / 限制 |
|---|---:|---|
| 两通道，sensor 原生 ROI 1280×480 | 6.528ms | 相对现有 720p 丢掉垂直视场；需新增 sensor 模式 |
| 两通道，sensor 原生 ROI 1280×360 | 4.896ms | 丢掉更多垂直视场；需调整接收、ISP、sender/viewer |
| ISP 将当前 720p 缩放成 480p/360p | sensor 仍约 9.792ms | 可减编码/传输负载，不缩短 sensor 的 720 行读出 |
| 恢复行级 wrap/slice 流水重叠 | sensor 本身不变 | 可减少读出后才开始编码的等待，但以前双路 wrap 有花屏，不能直接恢复默认 |

行 binning/跳读是否缩短模拟读出，要按具体模式验证，不能只按输出高度比例承诺。
同样，维持 720 行只裁水平宽度，在最小行长不变时也不会缩短这一预算。

## 后续 A/B 测试

A：现有两通道 RAW10、720p、约 99.23fps；B：四通道快速读出、相同输出尺寸、
相同帧周期、物理曝光、增益、码率和编码参数。之后再单独比较更高实际帧率。
本轮没有启动测试；之前直接 MMAP 快照停流已出现 `dma_buf_put` WARNING，
后续采集需要使用现有 USB 备用日志并检查初始化/停流，不能将旧 WARNING 忽略为通过。

- 先单路各 120 帧，验证完整 RAW/ISP 图案及真实场景、四条 lane、实际帧间隔、曝光和 CSI 错误。
- 再单进程双路各 120 帧，观察资源调度、帧号、丢帧、错行/花屏及内核日志；不自动长测。
- 关联同一源帧的 CSI SOF/EOF、ISP 输出、VENC 开始/完成、GetStream，记录 p50/p95/p99。
  时间戳参考点必须从驱动确认；不能把上游 SOF timestamp 误当成 ISP 完成时刻。
- 比较 SOF→EOF 是否接近减半，以及 EOF→编码完成是否反而增大。
  软件 A/B 通过后，再由最终光学测量确认端到端收益。
- 新驱动/DTS 通过 Distrobox 编译、测试和 SDK patch replay 后，再交用户手动烧录。
  本轮没有修改驱动/DTS、生成候选镜像或触发烧录。

本轮在 Ubuntu 22.04 Distrobox `aura-sdk` 中直接解析商家 INI 并核对当前驱动常量，
验证行/帧预算、四通道等帧周期候选值和曝光行数换算，全部通过；
这只是资料与算术核对，不是四通道硬件测试。`git diff --check` 通过。
