# AR0234：曝光、亮度与读出时间的关系

2026-10-15，四通道 #18 内核。此轮只读核对SSH控件、程序和公开资料；没有启流、修改曝光/增益或生成镜像。

## 当前控件与暗画面

查询时两路均为exposure400、analogue_gain32、digital_gain512、VBLANK762、pixel_rate360MHz；
查询时未见sender运行。这是保存的控件值，不能反推用户此前每一次观看画面的实际参数。
新模式每行6.8µs，**400行=2.72ms，735行=4.998ms**。不要继续使用旧两通道的13.6µs/行。

| 曝光行数 | 新模式曝光时间 |
|---:|---:|
| 148 | 1.0064ms |
| 294 | 1.9992ms |
| 442 | 3.0056ms |
| 588 | 3.9984ms |
| 720 | 4.8960ms |
| 735 | 4.9980ms |

室内短曝光偏暗可能来自照度、光圈、增益与色调处理；不能只凭5ms就认定画面必然应该够亮，
也不能直接判断硬件故障。短曝光下增加照明/打开可调光圈能增加有效光子，优先于数字提亮。
全局快门可以避免逐行时间错位，但长曝光仍会产生运动模糊。

当前sensor暴露曝光、模拟/数字增益、翻转和测试图案；ISP mainpath节点未暴露brightness/gamma控件。
sender源码没有接入RKAIQ初始化或完整AE/色调控制，viewer当前也没有可调EV/gamma命令行参数。
这些证据不能证明ISP硬件的gamma模块一定关闭；需要检查实际参数/灰阶响应。

模拟增益控件是`0x3060`寄存器编码，不是线性倍率：32=`0x20`约4倍、48=`0x30`约8倍、
64=`0x40`约16倍。32→48是约加一档，不是增加50%。参考
[驱动作者提交的增益换算实现](https://www.spinics.net/lists/devicetree/msg901623.html)。
当前数字增益已非最小值，避免只把所有数字推到最大；阴影噪声、饱和、有效动态范围和编码负载要一起观察。

可以保持曝光/数字增益不变，只将模拟增益32→48做一次亮度/噪声对照。
下次在板端启动约5ms的双路示例：

```sh
EXPOSURE=735 ANALOGUE_GAIN=48 DIGITAL_GAIN=512 /userdata/run-ar0234-stereo
```

这只是可试配置，本轮没有代用户应用，也没有实测这组画质。
若sender正在运行，可直接通过sensor的V4L2控件修改增益，不必重复初始化MPI。
下次launcher会重新应用环境变量/默认值，临时V4L2修改不等于永久默认。

数字增益、亮度和gamma可提高可见亮度，但不能补回缺少的光子或恢复已丢失的细节。
简单brightness加常数会抬黑；合理gamma/色调曲线更适合提亮暗部。未来可在现有Vulkan渲染pass内
增加手动EV/gamma，不需要为了这个功能引入额外帧队列；实际GPU耗时仍需测。
应先用固定曝光/增益和灰阶响应确认是缺光还是色调不合适，避免盲目重复gamma。

## max(曝光, 读出)与同一帧延迟

连续全局快门可以让**下一帧的曝光**与**上一帧的读出**重叠，改善连续输出的吞吐。
同一帧的光电积分必须先完成，再锁存/转移，之后输出该帧。不能把曝光当成与自身完整读出同步完成。
[相机厂商对global overlap的说明](https://andor.oxinst.com/learning/view/article/faqs-on-rolling-and-global-exposure)，
[AR0234参考驱动的自由运行/触发说明](https://github.com/Kurokesu/ar0234-rpi-driver/blob/main/README.md)。

在支持帧间重叠的简化模型中，`max(E,R)`更接近最短帧周期的约束之一，还要加上器件开销。
它不是该帧从看到场景到接收完成的延迟公式。当前实际帧周期仍为约10.08ms，
即使曝光5ms略大于4.89ms读出，也不因此必然降低约99fps。

忽略电荷转移、额外等待和后续ISP/编码/显示，并假设曝光结束后立即读出：

```text
帧N：曝光E → 电荷锁存/转移 → 读出R
曝光开始 → 接收完整帧：约 E + R
曝光区间中点 → 接收完整帧：约 E/2 + R
```

后一个量可用于理解图像信息年龄，不是本板实测的精确延迟；积分权重、实际采样相位、
触发模式、内部存储等待与CIF时间戳含义都可能影响它。
以R≈4.9ms做算术，1/3/5ms曝光的中点年龄预算分别约5.4/6.4/7.4ms，尚不包含后续阶段。
因此不能说“曝光小于4.9ms就完全不增加延迟”。

优化目标应是：在可接受运动模糊、噪声和高光饱和的条件下选择尽可能短的曝光，
并缩短读出与下游排队；不需要为了填满4.9ms主动把曝光拉长。
若想准确校准曝光相位，需要TRG/STRB或外部光信号与CSI SOF/EOF关联，不能靠CIF读出值单独推断。

## 4.9ms还能否缩短

当前720行、行长612、90MHz读出在公开参考驱动允许的最小行长/最大内部pixel clock边界。
保持完整1280×720、正常时钟范围，目前没有已验证的进一步缩短参数。
公开实现的四通道RAW8模式仍使用90MHz，因此降低位深不会自动让模拟读出更快。
[行长与clock限制的驱动实现](https://www.spinics.net/lists/devicetree/msg901623.html)，
[模式表](https://github.com/Kurokesu/ar0234-rpi-driver/blob/main/README.md)。

原生sensor ROI在行长不变的情况下：480行预算3.264ms、360行预算2.448ms，代价是垂直视场。
ISP把720p缩小不会减少sensor的720行读出。Binning是否改善光子利用和缩短读出，
需按具体模式验证，不能直接假设输出少一半像素就快一倍。

提高实际采样帧率可能减少等待下一帧的相位时间，行级ISP/VENC流水可能减少下游等待，
但两者不等同于缩短4.9ms传感器读出。双路wrap曾有花屏，不能直接重新开启当作稳定优化。
不在本轮修改已经验证的时序；后续优先做曝光/增益/照明/色调的画质对照。
